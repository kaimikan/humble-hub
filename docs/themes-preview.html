Ideas & optimisations to explore

Since we're reworking the theme layer anyway — things worth folding in:

The core mechanism (prerequisite for all of this)

  • Wire the terminal into apply(). Today the xterm theme is hardcoded; the whole "matched world" idea rests on apply() also setting term.options.theme (bg/fg + the 16 ANSI) per theme, on every live terminal.
  • One source of truth. Define each world once as { hub:{…}, term:{…} } and generate both the CSS variables and the xterm theme from it — no drift between the preview swatches and the real thing.

Quality-of-life

  • Follow the OS. Default to prefers-color-scheme on first visit (dark→lapis, light→codex) before falling back to the saved choice.
  • Group the picker by light / dark, and show a tiny terminal chip on each card so the matched pairing is visible at a glance.
  • Respect prefers-reduced-motion — the card hover lift / transitions.
  • A high-contrast / colourblind-safe variant (Nord and Catppuccin both ship daltonised palettes we could borrow) for accessibility.

Consistency clean-ups noticed while here

  • Accent semantics. The pigments mean things (--lapis=claude, --sanguine=go/launch, --verdigris=files). Keep that mapping stable across themes so muscle memory survives a theme switch.
  • Contrast budget. A couple of current themes ride low ink/​bg contrast (matrix faint text, dragon ochre on cream). Worth a quick WCAG pass per theme.
  • Scrollbars & selection currently ignore the theme — small but they break the illusion; easy to theme via the existing variables.

Playful, optional

  • Auto-by-time — warm (codex) by day, dark (lapis) at night.
  • "Surprise me" shuffle in the picker.
  • The Amber-CRT world below is included as a deliberate cautionary example: a monochrome terminal looks gorgeous but the diff colours collapse — proof of why accent separation matters.
